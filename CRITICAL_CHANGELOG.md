# Critical Changelog

Changes recorded here can break the locally configured Camoufox browser at runtime and are not captured by any published release. If the browser starts hanging clicks, hits the 22s worker deadline, and reports `camoufox_session_reset_required`, read this file first.

## 2026-09-19 - Verified element identity replaces the unverified `find` selector

- What: `find` no longer returns a structural CSS path that was never checked. `camoufox-backend/worker.py` replaces the old inline path builder with `_FIND_VERIFIED_SELECTOR_SCRIPT`, which ranks candidates (stable key attributes, then a document-unique `id`, then a keyed ancestor plus relative `:nth-of-type` segments, then a full structural path) and accepts one only when it resolves to exactly one element and that element is the matched node. `camoufox-backend/element_registry.py` adds a per-document node registry plus `element_inspect`, `element_expand`, and `visual_target`; `runtime.py` and `worker.py` wire the three actions; the Rust surfaces add `element-inspect`, `element-expand`, `visual-target`, and the MCP tools `agent_browser_element_inspect`, `agent_browser_element_expand`, `agent_browser_visual_target`.
- Why: the previous `find` returned a path whose uniqueness was never established, while the README and skill advertised it as a reusable unique selector. Duplicated `data-testid` values, repeated row buttons, and `:nth-of-type` chains that stop at a shadow boundary could all yield a path that resolved to a different node or to several, and acting subactions then delegated input to that guess.
- Risk: `find` can now fail with `camoufox_invalid_params` where it previously returned a questionable selector, so a caller that relied on a non-unique path must refine the locator or use `find nth`. `elementId` values are per document and per controller instance: they do not survive a navigation or reload, are not stable across sessions, and are never promised as durable identity for a re-rendered node. `visual_target` is main-frame only and rejects a selected non-main frame instead of mapping coordinates across frames. Selector candidates are resolved with `querySelectorAll`, which does not cross shadow boundaries, so an element inside an open shadow root is flagged with `inShadowRoot` rather than silently resolved.
- Activation: source only until the configured Rust binary is rebuilt and a fresh named daemon loads its embedded Python. No runtime reinstall, browser patch, or profile change is involved.

## 2026-09-17 - Screenshots carry inline base64 images and support full-page capture

- What: `screenshot` (MCP `agent_browser_screenshot`, CLI `agent-browser screenshot`) now returns the PNG inline as base64 in `data.image` and supports `fullPage` full scrollable capture (`--full` on the CLI). The worker emits `inline` screenshots into every screenshot response, including gesture `observe: "screenshot"` observations (which strip the image key as before, so gesture payloads stay small). MCP responses attach the image as an image content block (≤10 MiB base64) and remove `data.image` from structuredContent. The worker rejects `fullPage` documents above 30000px scrollHeight with `camoufox_invalid_params` and refuses inline full-page PNGs above 8 MiB before writing any file. New fields: `data.fullPage`, `data.image?`; full-page captures set `data.visualCapture: null` and register no captureId (viewport captures keep their captureId). CLI gains `--inline-image`; `--annotate` and element/selector captures stay rejected.
- Why: with the browser running inside the container bubble, screenshot PNGs landed on the container filesystem (`/opt/agent-browser-runtime/screenshots`), invisible to the host, so MCP `image_content_from_response` could never read the file and no client ever received a visual image. Transporting the bytes inside the response makes screenshots visual for every backend placement and enables whole-page visual review.
- Risk: screenshot responses grow to at most ~10.7 MiB of base64 over stdio; the 16 MiB worker output cap still bounds the envelope, and oversized full-page inline attempts fail fast with a clear message. Full-page PNG dimensions no longer equal the viewport, so the existing viewport-dimension staleness check is skipped for them; the pre/post capture-identity comparison still rejects captures taken while the page moved. A rebuilt binary and fresh daemon are required before the new fields appear.
- Activation: source edited; requires the Rust binary rebuild (backend Python is embedded), an MCP reconnect, and a fresh daemon/container. No persistent-profile impact.

## 2026-09-15 - Locale-spoof keys stripped from generated Camoufox fingerprints

- What: `_sanitize_fingerprint_config` in `runtime.py` removes `locale:language`, `locale:region`, `locale:script`, `locale:all`, and `navigator.language` from every generated fingerprint (decoding and rewriting the `CAMOU_CONFIG_<n>` env chunks in place). The Camoufox source patch `patches/locale-spoofing.patch` was also corrected: the `Locale::Language()/Region()/Script()` accessor hooks are removed with an explanatory note, keeping only the `Locale::GetDefaultLocale()` override.
- Why: with those keys present, the accessors made every internal Gecko `Locale` instance report the spoofed subtags, which corrupted `Intl.DisplayNames` process-wide — measured: `of('US')`, `of('GB')`, and `of('KY')` all returned the spoofed region's display name. Pages that validate locales through DisplayNames at hydration time (OpenRouter's gt-next: `Locale "en-US" is not valid`) threw and Next.js replaced the whole document with its error screen. Real OpenRouter sessions crashed reproducibly on every bubble launch; host juggler probes without a `locale` kwarg never crashed, and the `locale` kwarg reproduced the crash with any value.
- Risk: the page-visible `navigator.language` and `Accept-Language` now reflect the browser's real build locale (en-US) instead of a geo-coherent spoof, reducing locale-geo coherence; timezone and geolocation spoofs are unaffected. Sites that fingerprint locale will see a constant value across launches. The fingerprint's UA/screen/Canvas/WebGL/audio fields are untouched. Tests: `tests/test_fingerprint_sanitizer.py` (4 cases).
- Activation: source committed; requires the Rust binary rebuild (Python embedded), an MCP reconnect, and a fresh daemon/container. Existing persistent profiles keep their saved identities (which may still contain locale keys): delete the profile or point at a fresh path to get a sanitized identity.

## 2026-09-15 - Document response bodies survive eviction and raise to 8 MiB

- What: the network observer now evicts non-document records first (`network_observer.py`: `_evict_oldest` skips `resource_type == "document"` until only documents remain) and allows document bodies up to 8 MiB (`MAX_DOCUMENT_BODY_BYTES`), while fetch/XHR bodies keep the 1 MiB cap. `network request <id>` therefore keeps returning `responseBody` for the main page even after a heavy SPA fires hundreds of sub-requests, and large server-rendered pages (over 1 MiB, previously rejected as `oversized` or silently truncated to 1 MiB) are readable.
- Why: a real OpenRouter session hit both limits: the GLM-5.3 model page (~1.06 MB) was over the old body cap, and its ~500 asset requests evicted the document record before `network request` could read it. The page's own frontend then crashed, and the only accurate copy of what the server delivered was gone. Documents are the record an agent needs to recover page data from a broken frontend.
- Risk: memory for retained document handles rises to 8 MiB worst case per record and documents accumulate while non-documents evict around them; with the 500-record cap this is bounded (theoretical worst case is all-document traffic). Eviction order is no longer strictly FIFO when documents are present: the oldest non-document is evicted first, and with only documents left the oldest record is evicted as before. `test_network_observer.py::test_document_body_survives_subrequest_eviction` and `::test_document_body_allows_eight_mib` guard both behaviors.
- Activation: Python source change; requires the Rust binary rebuild (backend Python is embedded) and a fresh daemon. Skill guidance was updated in parallel (`skill-data/camoufox/SKILL.md` "Recovering page data from a broken frontend", `skill-data/core/references/camoufox.md`, `skill-data/core/SKILL.md` troubleshooting).

## 2026-09-15 - Geometry guard refusals no longer poison the session

- What: the os-native geometry guard's deterministic pre-dispatch refusals now raise `camoufox_invalid_params` instead of the generic `camoufox_error` (`camoufox-backend/osnative_input.py`: `_guard` window-mismatch refusals and `_screen_point` scale/out-of-window refusals). `_poison_failed_input` in `worker.py` exempts `camoufox_invalid_params`, so these refusals leave the session usable.
- Why: with two Camoufox windows mapped on the X display (for example after a page `window.open` popup), the guard correctly refused to dispatch input ("input would be ambiguous; close the extra windows and reobserve") but its `camoufox_error` classification poisoned the session as ambiguous input, forcing a full close/reopen reset. The refusal is sent before any XTEST event, so the recovery is exactly what the message instructs: clean up the extra window, reobserve, retry. A real YouTube session hit this: a `tab_close` cleanup then also failed against the poisoned state, and the whole session had to be reset just to stop a video.
- Risk: the exemption only covers the guard's refusal paths, which never dispatch XTEST events; post-dispatch ambiguity semantics are unchanged. Runtime/ambient failures (keymap remap at startup, viewport metrics read) keep `camoufox_error` and their conservative classification. A caller can no longer distinguish the guard refusal from an invalid-parameters failure by code alone; the message text still identifies the X display state. `tests/test_osnative_validation.py::GeometryGuardRefusalRegression` fails if the refusal code regresses to a poisoning classification.
- Activation: source committed; requires the Rust binary rebuild (Python is embedded), an MCP reconnect, and a fresh daemon/container.

## 2026-09-15 - x11vnc DAMAGE tracking enabled (removes -noxdamage)

- What: the bubble's x11vnc now runs with `-xdamage` instead of `-noxdamage` (`camoufox-backend/bubble.py`). The X DAMAGE extension lets Xvfb tell x11vnc exactly which screen regions changed; previously x11vnc polled the full 1920x1080 framebuffer for differences, re-reading and comparing roughly 8 MB by CPU on every pass, and a connected noVNC viewer made that continuous.
- Why: the human noVNC view lagged on simple scroll and animation while the browser itself had CPU headroom. Polling made viewer traffic cost proportional to the whole screen instead of the changed regions, on top of already fully software-rendered frames (no GPU in the container).
- Risk: DAMAGE can, in rare setups, miss invalidations and leave stale regions on screen; x11vnc 0.9.16 plus Xvfb 2:21.1 were smoke-checked in the bubble image (x11vnc started with `-xdamage`, completed the RFB handshake, no errors), and a quiet screen now yields zero unsolicited updates instead of constant polling. If a viewer ever shows a stuck region, moving the mouse over it or reopening the viewer repaints; reverting the single flag in `bubble.py` restores the old polling behavior. `libxdamage1` was already an installed dependency, so no image rebuild is needed.
- Activation: source committed; requires the Rust binary rebuild (bubble.py is embedded), an MCP reconnect, and a fresh daemon/container.

## 2026-09-15 - Deterministic bubble container names and fixed OrbStack noVNC domain

- What: under `--input-backend os-native` the daemon now names the bubble container after the session (`agent-browser-bubble-<session>`) instead of PID+nanoseconds; anonymous `default` sessions keep the ephemeral scheme. Before `docker run` the daemon removes any leftover container holding the same name (`docker rm -f`), because a fixed name collides after an unclean previous shutdown. Launch and `session info` additionally report `vncDomainUrl`: `https://agent-browser-bubble-<session>.orb.local/vnc.html?...`, the fixed noVNC address OrbStack derives from the container name; the port-based `vncUrl`/`nativeVnc` are unchanged.
- Why: the ephemeral name and port made the noVNC address different on every launch, so the human viewer URL could not be bookmarked or predicted. A session-derived container name makes the OrbStack domain stable: session `task1` is always `agent-browser-bubble-task1.orb.local`.
- Risk: two concurrent bubbles must now use distinct `--session` names (same session meant same ephemeral container before; now it means a name collision handled by removing the old container, so a second concurrent daemon with the same session would kill the first bubble's container). The daemon already refuses duplicate session names at the socket layer, so in practice this only affects processes that bypass the normal client path. `docker rm -f` of the stale name runs before every named launch; a container still writing state would be killed, which is the same recovery as an explicit close. Anonymous `default` sessions are unaffected. Verified against a live OrbStack container: OrbStack resolves the container-name domain for both HTTP (any exposed port) and HTTPS (443 routed to the first exposed port), including names with underscores and mixed case.
- Activation: source committed; requires the Rust binary rebuild, an MCP reconnect, and a fresh daemon/container. Unit test `camoufox_bubble_container_name_is_session_derived` guards the naming rule.

## 2026-09-15 - os-native Latin keymap remap and clean pre-dispatch validation failures

- What: the os-native backend now remaps missing Latin keysyms (á é í ó ú ñ ü ç ¿ ¡ €) onto unused X keycodes at worker startup via `XChangeKeyboardMapping`, so XTEST can type accented Spanish/French/German text; the X server fills the uppercase column, so Shift+keycode covers capital accents. Keymap validation moved before any journaling or input-attempt counting (`gestures/type.py`, `gestures/_common.py` `keyboard_press`, typed `press` in the worker): `type` and `press` call `validate_text`/`validate_press` on the dispatch first, and `_poison_failed_input` no longer poisons on `BackendError` with `camoufox_invalid_params`/`camoufox_unsupported`. Geometry guards after dispatch, unreleased journaled input, deadline expiry with attempted input, and transport failures keep the conservative reset-required classification.
- Why: the stock Xvfb keymap has no bindings for accented characters, so typing "Bogotá" failed with `no X keycode is bound to 'á'`; worse, that deterministic pre-dispatch failure poisoned the whole session as ambiguous input even though zero XTEST events had been sent, forcing a full close/reopen for a typo character.
- Risk: the remap is additive (existing layout bindings untouched; combos like Control+a verified unchanged) and requires one fully-empty keycode per missing keysym; if none are free the launch fails with a clear error instead of silently typing wrong characters. Validation-time failures now leave the session usable, which means callers can immediately retry with corrected text; agents that previously treated any input error as fatal no longer need to. Post-dispatch ambiguity semantics are unchanged.
- Activation: source committed; requires the Rust binary rebuild, an MCP reconnect, and a fresh daemon/container for the embedded Python (the remap runs at worker startup inside the container). `tests/test_osnative_validation.py` guards the poison classification: it fails if the validation-code exemption is reverted.

## 2026-09-15 - Camoufox os-native input backend (XTEST in a container bubble) and `--input-backend`

- What: `--input-backend juggler|os-native` (or `AGENT_BROWSER_INPUT_BACKEND`) selects the input dispatch backend. The new `os-native` backend routes mouse and keyboard dispatch through X11 XTEST against the private X display the browser runs on (via `camoufox-backend/osnative_input.py`), with no browser automation API involved in dispatch; element resolution, snapshots, screenshots, and evaluation stay Playwright. Under os-native the worker runs inside a container bubble (`AGENT_BROWSER_BUBBLE=1`, set by the daemon): `bubble.py` starts Xvfb 1920×1200, x11vnc clipped to the 1920×1080 window area, and noVNC on 6080 before launch, and tears them down on close. The Rust daemon spawns the worker with `docker run -i` (`agent-browser-camoufox:bubble` image), mounts the persistent profile at `/profile` (created 0700), publishes the VNC port, and injects `vncUrl`/`nativeVnc` into the launch response. The `juggler` default is byte-for-byte unchanged. Launch data also reports `inputBackend`.
- Why: the thesis-level input requirement: input that enters through the window system like a physical mouse of that display, per-session isolated graphical sessions, and no browser-internal automation APIs for dispatch. The macOS host cannot receive per-PID synthetic input (proven dead end), so the bubble delivers the isolated display on macOS via Docker/OrbStack.
- Risk: under os-native, element clicks replace Playwright's full actionability set with visible/scroll-into-view/in-viewport/box-stability checks; the `enabled` state is not pre-checked (the click reaches whatever the window system has at that point, so a covering overlay receives the click instead of the target), double-click timing is injector-based rather than Playwright-identical, and wheel scrolling approximates chunks as 100 CSS-px notches via buttons 4/5. A geometry mismatch before dispatch fails without sending input. Requires Docker/OrbStack and the bubble image; launch forces headless=false inside a bubble (the window renders on the private display). A config or CLI profile pointing at a Chrome profile directory is refused by the existing Camoufox identity protection, unchanged. The default backend and all non-os-native sessions are unaffected.
- Activation: source committed; requires the Rust binary rebuild, an MCP reconnect, a fresh daemon for the embedded Python, and a one-time `camoufox-backend/bubble/build.sh`. Close and relaunch keep the persistent profile; the container is removed on session close or daemon stop.

## 2026-09-15 - Camoufox ambient hover hold actions and MCP tool

- What: `hover_hold` (fields `selector`, `maxMs`) and `hover_hold_stop` daemon actions, the `agent_browser_hover_hold` MCP core tool for Camoufox, and the `hover-hold <selector> [--max-ms N]` / `hover-hold stop` CLI commands. Starting a hold resolves the selector in the selected frame scope, requires exactly one visible element with a bounding box, dispatches a native mouse move to its center, and registers a background ambient micro-movement task (randomized 200–400ms intervals, ±2px per-axis jitter around the start point) that keeps hover-revealed UI visible for up to `maxMs` (1000–120000, default 30000). Starting while a hold is active replaces it. Any input or lifecycle action, including `hover_hold` itself, awaits the hold's stop before dispatching; read-only observation (screenshots, snapshots, DOM reads, waits, inspection) continues during the hold. Explicit stop returns `{stopped, heldMs}`.
- Why: hover-revealed UI such as player controls auto-hides between agent steps, so observation and coordinate gestures had to race the hide timer. The hold keeps native mouse micro-movement at a selector so screenshots, DOM reads, geometry, and coordinate gestures can happen at leisure while the revealed UI stays visible.
- Risk: the hold start is a new mutating action and invalidates captures and DOM refs like other input actions; the ambient loop itself never invalidates captures, refs, or DOM refs. A hold moves the real mouse, so concurrent manual use of the visible browser fights the micro-movement. Holds auto-stop before input and lifecycle actions, but a long `maxMs` hold otherwise keeps the cursor near the selector. Both actions reject non-Camoufox engines; `hover_hold_stop` does not implicitly launch a browser.
- Activation: source committed; requires the configured Rust binary rebuild, an MCP reconnect, and a fresh daemon for the embedded Python to load.

## 2026-09-15 - Camoufox MCP core replaces pagination tools with semantic find

- What: the Camoufox MCP `core` profile no longer exposes `agent_browser_page_outline`, `agent_browser_page_links`, or `agent_browser_dom_chunk`; it now exposes `agent_browser_find`. The find-family actions `getbyrole`/`getbytext`/`getbylabel`/`getbyplaceholder`/`getbyalttext`/`getbytitle`/`getbytestid`/`nth` are now supported by the Camoufox engine: the worker builds the Playwright locator in the selected frame scope, rejects zero matches, and rejects ambiguous matches for acting subactions with `camoufox_invalid_params` before any input, derives a unique CSS selector for the match, and delegates acting subactions to the existing `click`/`fill`/`check`/`hover` handlers with that selector, preserving the motion profile and input guards. The read-only `text` subaction returns `{found, count, selector, text}` for the first match without invalidating captures or refs; acting subactions invalidate them like other mutating actions. The omitted subaction defaults to `click`. The three pagination commands remain unchanged as CLI commands and daemon actions.
- Why: the paginated reading tools duplicated coverage already available through `agent_browser_snapshot` and `agent_browser_get_html`, and their cursor/ref bookkeeping added fragile state. `agent_browser_find` gives one semantic call that resolves to a precise, reusable CSS selector and rejects ambiguous targets instead of acting on a guessed match.
- Risk: existing MCP clients configured with the Camoufox server see three fewer tools and one new tool after a rebuild and MCP reconnect. Agents that relied on `page_outline`/`page_links`/`dom_chunk` through MCP must switch to `agent_browser_get_html` (selector `html` for the whole document element's contents), `agent_browser_find`, and `agent_browser_snapshot`; CLI commands are unchanged, so shell workflows keep working. Profiles that do not include `core` are unaffected. Nothing in the browser runtime or installed profile changes.
- Activation: source committed; requires the configured Rust binary rebuild, an MCP reconnect, and a fresh daemon for the embedded Python to load.

## 2026-09-15 - Host-coherent launch fingerprint policy (NBF routine recipe)

- What: Camoufox launches now pass `os` matching the host (`macos` on Darwin, `windows` on Windows, otherwise `linux`), a fixed `window` of 1920x1080, `block_webrtc=True`, and `geoip=True` when the geoip extra and a local GeoIP database are present in the managed runtime. A failed public-IP or GeoIP lookup retries the launch once without geoip with a stderr warning instead of failing every launch. `humanize` still comes from the motion profile.
- Why: this mirrors the NewBuildersFinder routine recipe (`scraper_engine_sdk.browser.build_browser_kwargs`). Previously no `os`, `window`, `block_webrtc`, or `geoip` were passed, so fresh launches generated a random-OS fingerprint (the configured `personal` profile identity is Windows on a macOS host) with no IP-based timezone, locale, or geolocation coherence, which bot managers flag.
- Risk: WebRTC is now disabled in all sessions (`media.peerconnection.enabled=false`), which breaks sites that require WebRTC. Fresh profiles and ephemeral sessions present a host-matched fingerprint instead of a random-OS one. Camoufox config merges are no-clobber, so a persistent profile's saved identity keeps its fingerprint and gains only the WebRTC pref and, when available, IP-coherent values it never saved. The geoip part stays inactive until an authorized runtime reinstall installs `camoufox[geoip]` and pre-downloads the GeoIP database via `bootstrap.py`; that reinstall also re-resolves the official browser and requires re-applying `scripts/camoufox-guard-patch.py`.
- Activation: source-only until the configured Rust binary is rebuilt and a fresh daemon loads its embedded Python. The `os`/`window`/`block_webrtc` parts need no runtime reinstall; geoip requires the reinstall above.

- A local headed-launch experiment forced `gfx.webrender.compositor=false` to investigate visible stuttering. The user initially reported partial improvement, then freezing and a native `EXC_BAD_ACCESS` crash on the Renderer thread with Camoufox 152.0.4-beta.30. ## 2026-09-14 - Same-window tab creation for `tab new`

- What: `tab new`/`agent_browser_tab_new` now creates the new page with `window.open(url, '_blank')` from the live active page, so Firefox hosts it as a tab of the existing browser window. With no usable active page (fresh launch, closed active tab) or a blocked popup, it falls back to `context.new_page()`, which Camoufox's Juggler hosts as a separate window as before. Tab registration, refs, snapshots, and switching are unchanged; the returned tab works identically either way.
- Risk: pages that aggressively block scripted popups could make the first creation attempt fail before fallback; the fallback preserves the previous behavior in that case. Sites could theoretically observe a `window.open` call on the active page (Camoufox evaluation runs in an isolated world, and the call matches ordinary popup traffic). Tab-ordering inside the window's tab strip now depends on Firefox's own placement instead of always appending a new window.
- Activation: source-only until the configured Rust binary is rebuilt and a fresh named daemon loads its embedded Python. Older daemons keep opening separate windows. No managed runtime assets, browser profiles, or installed browser files were edited.
